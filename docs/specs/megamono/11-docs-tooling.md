# 11 — Docs Tooling: Graph, Generators, Archiving

Implementation layer for `spec-megamono-0004`. That document defines the taxonomy and the rules; this one defines the machinery that makes them hold.

## Content Collections as the derived graph

The corpus needs a queryable graph — to validate that referenced IDs resolve, to find inbound references before archiving a document, to generate `INDEX.md`, and to let internal tooling render docs.

Hand-rolling that means writing a front-matter parser, a schema validator, a watcher, and a type generator. [Content Collections](https://www.content-collections.dev/) supplies that machinery. V1 pins `@content-collections/core` to `0.15.2` and Zod to `>=4.1 <5`; upgrades require the fixture suite because this is a pre-1.0 dependency.

### The non-negotiable constraint

> **`docs/` stays plain markdown on disk. The graph is derived, never required.**

If reading a decision record depends on running a build, the agent substrate is broken. An agent must be able to `cat` a file and understand it, in a fresh clone, with no toolchain.

Content Collections produces a **derived artifact alongside** the source. Everything it enables — validation, typed access, reference integrity — is additive. Delete `.content-collections/` and the corpus is unchanged.

### Two source collections plus two generated entry points

```ts
// content-collections.ts — abbreviated only by the validateTypeSpecificFields body
import { defineCollection, defineConfig } from '@content-collections/core';
import { z } from 'zod';

const repoDocSchema = z
  .object({
    id: z.string().min(1),
    type: z.enum(['spec', 'plan', 'decision', 'audit', 'research', 'report']),
    status: z.string().min(1),
    visibility: z.enum(['internal', 'public']).default('internal'),
    visibility_reviewed_at: z.iso.datetime().optional(),
    projects: z.array(z.string()).min(1),
    topics: z.array(z.string()),
    summary: z.string().min(1),
    date: z.iso.date(),
    supersedes: z.string().nullable().default(null),
    references: z.array(z.string()).default([]),
    external_references: z.array(z.string()).default([]),
    branch: z.string().optional(),
    completed_at: z.iso.datetime().optional(),
    aborted_because: z.string().min(1).optional(),
    revisit_when: z.string().min(1).optional(),
    migration_path: z.string().min(1).optional(),
    standard: z.string().min(1).optional(),
    producer: z.string().min(1).optional(),
    generated_at: z.iso.datetime().optional(),
    retention_days: z.number().int().positive().optional(),
  })
  .superRefine(validateTypeSpecificFields);

const repoDocs = defineCollection({
  name: 'repoDocs',
  directory: 'docs',
  include: [
    'specs/**/*.md',
    'plans/**/*.md',
    'decisions/**/*.md',
    'audits/**/*.md',
    'research/**/*.md',
    'reports/**/*.md',
  ],
  exclude: ['**/README.md', '**/OVERVIEW.md', '**/INDEX.md'],
  schema: repoDocSchema,
});

const archivedDocs = defineCollection({
  name: 'archivedDocs',
  directory: 'docs/archives',
  include: ['**/*.md'],
  exclude: ['**/INDEX.md'],
  schema: repoDocSchema,
});

export default defineConfig({ content: [repoDocs, archivedDocs] });
```

Content-level collections are defined separately, per the two-corpora split, with their own schema (`title`, `description`, `published`).

After validation, the executor emits two stable entry points: `content-collections/repo-docs` contains the hot collection and is restricted to internal apps; `content-collections/public-repo-docs` is generated by filtering `visibility: public` and is the only entry point public apps may import. Archived documents are never exported to public applications.

### Validation as a build gate

Content Collections warns on invalid content in development and fails the build in CI. That maps cleanly onto the conventions:

| Check                                                                | Enforced by                                   |
| -------------------------------------------------------------------- | --------------------------------------------- |
| Required front matter present                                        | Schema                                        |
| `topics` from controlled vocabulary                                  | Schema enum, generated from `megamono.json`   |
| `status` valid for this `type`                                       | Schema refinement                             |
| `aborted` plan has `aborted_because`                                 | Schema refinement                             |
| Every `references` ID resolves across hot and archive collections    | `megamono-docs:validate` post-validation      |
| Every ID is globally unique                                          | `megamono-docs:validate` post-validation      |
| Qualified external reference has valid syntax                        | Schema refinement                             |
| Public record has `visibility_reviewed_at`; internal record does not | Schema refinement                             |
| Changed public content advances `visibility_reviewed_at`             | `megamono-docs:validate` Git-diff check in CI |
| Public entry point contains no internal record                       | Generated-entry-point assertion               |

That last one is the payoff of ID-based cross-referencing. A dangling reference becomes a build failure rather than something discovered months later.

### In Nx

The `megamono-docs` project exposes the targets from `spec-megamono-0000`. `validate` declares `.content-collections/` as its output so results cache and `affected` work. The directory is gitignored. `INDEX.md` and `docs/archives/INDEX.md` are committed because they must be readable without a build.

Under the ownership modes in `spec-megamono-0014`, committed indexes are `derived`: the index executor regenerates them from the validated corpus and byte differences fail the corresponding check. A repository-docs Content Collections configuration created wholesale by Megamono is `managed`; an existing loader configuration is repository-owned and receives only a previewed integration proposal. This ownership does not extend to content-level emissions owned by Playstack. `DESIGN.md` and document skeletons are `seeded`. Creating the corpus directories never grants Megamono ownership of documents later placed inside them.

## Generators

| Generator                                                         | Does                                                                                                                   |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `npm exec nx g @megamono/plugin:docs-init`                        | Scaffold the IA, config, `AGENTS.md`, `CLAUDE.md` pointer, `.agents/skills`, `.claude/skills` symlink, and `DESIGN.md` |
| `npm exec nx g @megamono/plugin:docs-spec <project>`              | Numbered spec suite skeleton                                                                                           |
| `npm exec nx g @megamono/plugin:docs-decision "<title>"`          | Dated decision record with a slug ID                                                                                   |
| `npm exec nx g @megamono/plugin:docs-plan <project> "<title>"`    | New plan, `status: backlog`                                                                                            |
| `npm exec nx g @megamono/plugin:docs-research "<title>"`          | Research record                                                                                                        |
| `npm exec nx g @megamono/plugin:docs-audit <target>`              | Audit skeleton against a named spec                                                                                    |
| `npm exec nx g @megamono/plugin:content-lib <name>`               | Content-level collection library                                                                                       |
| `npm exec nx g @megamono/plugin:content-type <collection> <name>` | Document type within a content lib                                                                                     |

IDs and numbering are automatic. Manual numbering is where suites drift, and manual IDs are where reference integrity dies.

`docs-init` reuses the same `docs`, `agents`, and `skills` module primitives and `.megamono/artifacts.json` ownership library as `workspace-init`. It is a focused entry point, not a second template or provenance implementation.

Generators own record shape at creation time, not record content afterward. Once a spec, plan, decision, research record, audit, or design brief is written, it is repository-owned and no plugin upgrade rewrites its prose or front matter. Only an explicitly invoked lifecycle executor may apply the narrowly specified metadata transition in this spec.

### Content lib generators

`content-lib` scaffolds a content-level library: directory layout, `content-collections.ts` config, tsconfig path mapping for the generated import, the Nx target with `outputs` wired, and `.content-collections/` gitignored.

`content-type` adds a document type to an existing lib — collection definition, content directory, schema stub.

The emitted config imports transforms from `@playstack/content` (slug, reading time, TOC, date normalization). **This is the allowed direction:** Megamono generates, Playstack provides. A generator emitting a runtime import is not a violation; the reverse — Playstack importing anything Megamono — remains prohibited (`spec-megamono-0007`).

The published generators are acceptance-tested from packed Megamono output against the Free-tier `@playstack/content` yalc artifact. The npm and pnpm fixtures build the generated library, preserve local package addresses, and verify that unchanged generator reruns are stable.

The graph edge falls out naturally. Touching content marks consuming apps affected.

## Archiving

Splits along the line already established in `spec-megamono-0005`: **skills report, they never auto-edit.**

### Skill: `archive-review`

Judgement. The scheduled health cadence identifies candidates (`spec-megamono-0008`); a maintainer or agent explicitly invokes the skill as defined by `spec-megamono-0005`.

Flags:

- Active plans whose branch is merged/deleted or whose last material update exceeds the configured threshold
- Specs describing projects no longer in the graph
- Research superseded by a later decision on the same topics
- Documents marked `public` whose content changed after `visibility_reviewed_at`

Output is a proposal in the weekly health issue. It moves nothing.

### Executor: `npm exec nx run megamono-docs:archive`

Mechanics. Deterministic, and therefore not an agent's job — once the decision is made there is no judgement left, and code moves files more reliably than an agent does.

Steps:

1. Require `--id` and a type-valid terminal transition:
   - plan: `--status=completed|aborted`; aborted additionally requires `--reason`
   - spec: `--status=retired|superseded`; superseded additionally requires `--replacement-id` whose spec declares `supersedes: <id>`
   - research: `--status=complete`; already-complete research may omit the flag
   - all other types: refuse because they do not archive
2. Resolve the record and validate the requested transition in memory.
3. Rename the document to its mirrored path under `docs/archives/` and apply allowed lifecycle metadata in the same write plan. Plan updates `status`, `completed_at`, and optional `aborted_because`; spec updates `status`; active research updates only `status`.
4. Rewrite no references — IDs are stable.
5. Regenerate both indexes and validate the combined corpus.
6. Apply the plan only after every prior step succeeds. `--dry-run` prints it and writes nothing.

Step 3 is the point of ID-based references. A path-based corpus would need a rewrite pass across every referencing document, including append-only decision records that should not be edited.

**Reversible.** Every changed path is reported. Because the documents are tracked, normal version-control restore remains available; the executor does not commit.

### Retention: `npm exec nx run megamono-docs:prune-reports`

`reports/` is not archived, it is pruned. Scheduled health runs create no report files; this target applies only to explicitly persisted command output.

Default window: 84 days, overridden per record by `retention_days`. The target prints expired IDs by default and deletes only with `--confirm`; deletions remain recoverable from version control.

## Lint rules

Added to the table in `spec-megamono-0006`:

| Rule                       | Severity | Checks                                                        |
| -------------------------- | -------- | ------------------------------------------------------------- |
| `docs-front-matter`        | Error    | Required fields present                                       |
| `docs-topic-vocabulary`    | Error    | `topics` from the controlled list                             |
| `docs-reference-integrity` | Error    | Every `references` ID resolves                                |
| `docs-visibility-boundary` | Error    | Public-facing apps import only `visibility: public` repo docs |
| `docs-corpus-direction`    | Warning  | Content-level docs don't reference repo-level docs            |
| `docs-abort-reason`        | Error    | `aborted` plans carry `aborted_because`                       |

Public-facing vs. internal is declared per-app by Nx tag, the same mechanism as the `platform:worker` boundary rule.

## Risks

**Content Collections is substantially a single-maintainer project.** That is the same funding fragility that killed Contentlayer, and it is worth naming rather than discovering.

The mitigation is already structural: front matter and file layout are plain markdown conventions, not tool-specific formats. If the tool goes unmaintained, the corpus is unaffected and the graph is rebuildable by anything that parses YAML front matter. **Do not adopt features that would make the corpus unreadable without the tool.**

**Schema churn across two collections.** Repo-level and content-level schemas evolving independently is correct, but adding a field to one and forgetting the other is an easy mistake. The generators are the mitigation — they own the front-matter template.

## Acceptance criteria

- The checked-in Megamono corpus builds with `@content-collections/core@0.15.2` and validates without exceptions.
- `README.md`, `OVERVIEW.md`, and generated indexes are not parsed as corpus records.
- Duplicate and dangling IDs fail with both source paths in the diagnostic.
- A reference from the hot corpus to an archived record and the reverse both validate.
- The public generated entry point contains only public records and is the only repo-doc entry point allowed in a public app fixture.
- Every generator is idempotent and produces IDs in the formats defined by `spec-megamono-0004`.
- Archive dry-run and execution produce the same ordered path plan; a failed validation produces no changes.
- Index output is byte-for-byte deterministic across two runs.
- Plugin upgrades never rewrite seeded document bodies, while derived indexes regenerate and pristine managed loader plumbing may update through the common artifact registry.
- Creating or ejecting docs tooling never claims, moves, or deletes descendant repository documents.
