# 10 — Import: Absorb a Repo Into a Megamono

## Why this exists

`spec-megamono-0009` makes a repo a valid host. Import is what lets a second repo move into it without losing its past.

This is the operation that makes "consolidate instead of coordinate" a real answer to Polygraph rather than a slogan. Most teams do not stay fragmented because they prefer it — they stay fragmented because consolidating means either losing history or spending a week on a merge nobody wants to own.

**The hard parts are not file movement.** They are history preservation, dependency reconciliation, build translation, and import rewriting. Nx has an import command; it does not carry the load on the last three, and it assumes JS throughout.

## Prerequisite

The target repo must already be a Megamono host — converted (`spec-megamono-0009`) or created (`spec-megamono-0002`). Import into an unstructured repo is refused, because there is no `apps/` convention to import _into_ and no lint layer to validate the result.

The target working tree must be clean and checked out on a non-default branch with an upstream default branch available as the rollback point. A local source tree must also be clean. A remote source is cloned to a temporary directory and resolved to an immutable commit before analysis.

## Invocation

Import is an executor because preserving history requires Git commits and is not representable as an Nx virtual-tree generator.

```text
npm exec nx run megamono:import -- \
  --source=<path-or-git-url> \
  --ref=<branch-tag-or-sha> \
  --expected-source-sha=<full-sha> \
  --name=<project-name> \
  --destination=apps/<name> \
  --history=subtree \
  --verify=build
```

Without `--execute`, the command is analysis-only and writes nothing. Its report prints the full resolved source SHA. Execution requires `--execute`, that SHA repeated as `--expected-source-sha`, an explicit history strategy, and resolutions for every dependency, name, alias, environment-variable, and path collision. A changed ref fails preflight rather than importing different code from the analyzed source. In non-interactive CI, any missing resolution exits `4` before the first commit.

Source URLs containing embedded credentials are rejected. Authentication is delegated to the user's configured Git credential mechanism; credentials never enter the plan, report, process arguments generated by Megamono, or committed files.

## Phases

### Phase 1 — Analyze both sides

Read the source repo without modifying either. Produce a reconciliation report covering:

- Where the source app will land in `apps/`
- Every dependency where source and target disagree on version
- Build/test/lint commands that need translation to targets
- Non-JS surfaces and whether the relevant inference plugin is present
- Name collisions: project names, path aliases, npm scopes, env var names

**Name collisions are the underrated one.** Two repos independently owning `@app/shared` or `DATABASE_URL` is common, and discovering it after the merge means untangling it inside a combined history.

The report is approved before anything is written.

### Phase 2 — Graft history

The genuinely hard phase.

Options, in order of preference:

| Strategy                     | Preserves                               | Cost                                |
| ---------------------------- | --------------------------------------- | ----------------------------------- |
| `git subtree add`            | Full history, single commit graft point | Paths are unprefixed in old commits |
| `git filter-repo` then merge | Full history with rewritten paths       | Slow on large repos; rewrites SHAs  |
| Squash import                | Nothing but a snapshot                  | Trivial; sometimes correct          |

**V1 defaults to subtree.** It preserves history, needs no rewriting of the source, and the graft point is legible in the log. The source is first grafted under `.megamono-import/<name>/`; the integration commit then moves app-owned files to their final paths and routes repository docs into the centralized corpus. Its weakness is that pre-import commits reference paths below the staging prefix — `git log --follow` can degrade at the boundary.

`filter-repo` fixes that by rewriting the source's paths to their new prefix before merging, at the cost of new SHAs. Offer it explicitly for teams that care about `--follow` continuity more than SHA stability.

**Squash is a legitimate choice** and should be offered without judgement. Sometimes the source's history is genuinely not worth carrying — a prototype, a vendored template, a repo whose commits are all "wip." Do not moralize about it.

Whichever strategy is chosen, execution generates an accepted decision record containing the source URL without credentials, resolved SHA, destination, strategy, and acknowledged tradeoffs. Six months later, someone will ask why history behaves oddly before a certain date, and the answer should be findable.

### Phase 3 — Reconcile dependencies

The phase most likely to produce a broken workspace, and where Megamono's graph earns its place.

Same logic as `spec-megamono-0008`, applied at merge time. For each conflicting dependency, resolve into one of:

- **Alignable** — one version satisfies both sides; align it.
- **Constrained** — an external constraint (Expo SDK, Swift toolchain, PHP platform) pins one side. Do not force alignment. Isolate, and record why.
- **Deliberate** — divergence is intended. Record as an informed deferral with a revisit trigger.

**Never silently take the higher version.** That is the default behaviour of naive merges and it is how an import breaks the app that was working before the import.

Where isolation is required, prefer package-manager-native mechanisms that remain compatible with npm workspaces. A root `overrides` rule is allowed only when it satisfies both sides; nested independent installs are not accepted because they make lockfile and affected behavior ambiguous. An unsatisfied conflict blocks the import.

### Phase 4 — Translate builds

Source build commands become applicable Nx targets: `build`, `test`, and `lint`, plus `deploy` only when the source already defines it. As in convert: **wrap, don't rewrite.** The imported app should build the same way it did the day before.

### Phase 5 — Rewrite imports and validate

Cross-boundary relative imports become path aliases. Then validate: the imported app builds, its tests pass, the graph shows the edges it should, and lint runs in warning mode.

**Validation gate:** if the imported app does not build, the import is not finished. The branch is not merged. Half an import is worse than none — it leaves a repo where one surface is broken and the cause is buried in a merge commit.

### Phase 6 — Fold in the docs

Source docs migrate into `docs/specs/<project>/` with front matter applied (`spec-megamono-0004`), and existing decision records are absorbed with their original dates preserved.

Preserving dates matters: an imported decision from 2024 is still a decision, and back-dating it to the import would misrepresent the corpus. `INDEX.md` regenerates over the combined set.

## Incremental, not big-bang

Import absorbs **one repo at a time.** Each import ends with a working repo. Ten repos means ten operations, each independently revertable.

A single operation that absorbs everything is the version that gets abandoned halfway through, leaving a repo in a state nobody understands.

## Failure and reversibility

- Refuse on a dirty tree in either repo.
- Operate on a branch in the target. The source repo is **read-only throughout** — it is never modified, so an abandoned import costs nothing on that side.
- **Do not archive or delete the source repo as part of import.** That is a human decision made after the merged result has been trusted for a while. An import tool that deletes the fallback is an import tool that cannot be trusted.
- Print a Markdown-capable summary documenting the source SHA, strategy, versions aligned, conflicts isolated, and collisions renamed. `--report=<path>` persists it only when explicitly requested.

Execution creates a history-graft commit first. It then applies integration changes without committing, installs from the root lockfile, and runs the selected validation. Only successful validation creates the final integration commit. A failure leaves the branch and working tree intact with `MEGAMONO-RECOVERY.md`; the executor never rewinds history automatically and never pushes.

## V1 decisions and deferrals

- Subtree is the default history strategy. `filter-repo` is opt-in and requires the external binary range recorded in `@megamono/plugin/compatibility.json`; preflight refuses an absent or incompatible binary. Squash requires `--allow-history-loss` in addition to `--execute`.
- A source may contain a single JS app plus SwiftPM or Cargo surfaces when the matching Wave 1 plugin is installed. Toolchain-version conflicts block execution and appear in analysis; they are never silently reconciled.
- The source repository remains read-only. Import never writes a redirect, archives the source, changes its default branch, or modifies its settings.
- Monorepo-into-monorepo and organization-wide analysis are out of v1 scope.
- A hosted GitHub App is deferred. V1 is local only, creates no PR, and requests no GitHub token.

## Acceptance criteria

- Analysis produces stable output for local and remote sources and performs zero writes in both repositories.
- Subtree, filter-repo, and squash fixtures preserve exactly the history promised by their selected strategy; squash cannot execute without `--allow-history-loss`.
- Dirty trees, default-branch execution, unresolved SHAs, unsupported source shapes, missing plugins, and unresolved collisions fail before the graft commit.
- Dependency reconciliation never selects a version merely because it is newer; every conflict has an accepted resolution in the execution plan.
- Successful imports build, test, lint, and expose expected graph edges from a clean root npm install.
- Failed validation leaves the source untouched, creates no final integration commit or push, and writes a recovery report on the target branch.
- The executor is idempotent by source SHA and destination: an already completed import exits `0` with no new commit; a partial prior import exits `3` with recovery guidance.
